# Naming Conventions

## Purpose
This document defines naming patterns for repositories, applications, features, profiles, APIs, and ecosystem protocols.

## Repository Naming
- Repository names should be clear and human-readable.
- Prefer PascalCase for top-level product or ecosystem repositories when already established.
- Examples:
- `StarsongDesignSystem`
- `StreamSignal`
- `TideReader`
- `TuberSwitch`

## Application Naming
- Application names should be concise and purpose-oriented.
- Avoid names that are so generic they blur together.
- Product names should remain stable once published unless there is a strong reason to rename.

## Feature Naming
- Feature names should describe user value rather than implementation detail.
- Prefer names like `Destination Groups`, `Recovery Center`, or `Overlay Settings` over internal-only vocabulary.

## Profile Naming
- Profile names should reflect user intent and workflow context.
- Good examples:
- `Music Stream`
- `Gaming Stream`
- `Singer Avatar`
- `Album Art Overlay`

Avoid names that are only meaningful to internal implementation.

## API Naming
- Use clear, stable, descriptive endpoint names.
- Prefer nouns and action resources that match ecosystem concepts.
- Keep versioning explicit when stability matters.

## SIP Naming
- Protocol documents should be versioned and concise.
- Preferred naming pattern:
- `SIP-v1`
- `Starsong-Profiles-v1`

## Document Naming
- Major standards should be versioned when appropriate.
- Use title-style filenames with clear subject naming for human-facing docs.
- Keep protocol and ecosystem documents easy to scan in directory listings.
